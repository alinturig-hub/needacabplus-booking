# Booking database ownership

## Target

Need A Cab Plus owns the operational PostgreSQL database and the booking write path. TaxiCRM reads the same booking rows for customer profiles and reporting. A booking is stored once, with `(provider, externalId)` identifying an Autocab booking. TaxiCRM keeps its CRM-specific writes, such as customer tags and predictions, separate from the operational booking writer.

Its Prisma `Booking` model contains the complete Autocab booking, with dependent `BookingLocation`, `BookingVia`, `WebhookEvent`, `BookingTimelineEvent`, and `BookingSnapshot` records. Its webhook handler writes bookings and related customer records in transactions.

Its live customer booking path writes there, while admin search, dispatch views and the map can read TaxiCRM directly. Its webhook normalization code can also write to the smaller table, but this is not equivalent to TaxiCRM's full booking model.

## Physical database choice

The owner chose a **new dedicated PostgreSQL database for Need A Cab Plus** on 13 October 2026. Restore the complete TaxiCRM database and the smaller Need A Cab Plus database into it, then point both applications to the new resource with separate database roles. This gives a clean resource owner and leaves both existing databases intact during validation. The server showed about 1.18 TiB available before the isolated restore, enough room for the roughly 49 GB source, 3.5 GB local database, temporary archives and rollback copies.

Do not use the stale backup alone as the final live copy: webhook events and CRM writes continue after the backup. A tested catch-up process or a controlled final write pause with a fresh snapshot must reconcile the gap before switching either application. After cutover, only the new database receives operational booking and tracking writes; the old resources are kept read-only for a defined rollback window and then retired. TaxiCRM may continue to write its own CRM-specific profile and prediction tables in the shared database, but its role must not write canonical operational booking tables once that work is reassigned.

1. **Preflight:** Run `node scripts/booking-migration-preflight.mjs` from the Need A Cab Plus runtime, where `TAXICRM_DATABASE_URL` and `DATABASE_URL` are configured. Keep the JSON result. Confirm actual table collisions, database sizes and booking foreign keys. Obtain a restorable backup of **both** databases and verify it in an isolated database.
2. **Prepare the shared database:** Restore both backups into a new isolated PostgreSQL database, starting with TaxiCRM and then Need A Cab Plus. Check collisions among all relation and custom type names first. Preserve all IDs and timestamps. Verify row counts and foreign keys before connecting either live application to the shared database. Keep the existing `Booking` model intact; do not flatten it into the lowercase `bookings` table.
3. **Prepare application code:** Move Autocab webhook ingestion and booking status writes to Need A Cab Plus against the restored `Booking` model. Keep the webhook idempotency key and forward-only status rules. Update Need A Cab Plus search, dispatch, customer history and map reads to use its own database. Give TaxiCRM a database role that can read operational booking tables but cannot write them. Route CRM tag and prediction writes to CRM-owned tables. TaxiCRM currently also updates `Booking.normalCustomerId` and enriches booking locations, so reassign those writes before revoking its booking-table permissions. Preserve its revenue calculations and account rules while the new owner adds equivalent reporting.
4. **Cut over once:** The owner prefers no user-visible pause. Before switching, provide a durable ingress buffer for accepted webhook and booking requests, or prove a single-writer handoff with in-flight requests drained and the last source write watermark recorded. Apply the final delta, point both applications at the new database, then release buffered work. Record the last source event and first target event. Never enable two independent booking writers. If a durable buffer and a safe handoff cannot be established, arrange a brief controlled write pause with explicit retries instead of risking lost or duplicated bookings.
   For Need A Cab Plus, set `DATABASE_URL` to `needacabplus_shared_app`, `TAXICRM_DATABASE_URL` to `needacabplus_shared_reader`, and `DATABASE_SCHEMA_MANAGED_EXTERNALLY=true`; remove the old `TAXICRM_BOOTSTRAP_DATABASE_URL`/reader-bootstrap settings. ## Constraints

- The existing lowercase `bookings` table must not be treated as a complete replacement for TaxiCRM's `Booking` table. The models differ and a direct row copy would lose data.
- Changing the location of the database alone does not transfer booking ownership: the webhook writer and every other booking write path must also move.
- Do not switch the live connection strings before the shared database has been restored, code deployed and the event gap reconciled.

## Booking writer inventory for handoff

- TaxiCRM's Autocab ingress stores raw `WebhookEvent` rows, then `processWebhookEvent` applies each event in one Prisma transaction. Booking effects span `Booking`, `BookingLocation`, `BookingVia`, `BookingTimelineEvent`, `BookingSnapshot`, status timestamps, and the `Booking.normalCustomerId` customer link. Preserve the transaction, idempotency key and status transition rules when moving this processor.
- TaxiCRM also writes booking tables outside the main webhook transaction: fare and cached-place backfills update `Booking` and `BookingLocation`; Geoapify enrichment updates `BookingLocation`; timeline and snapshot services can create dependent records. Inventory their live callers and either move or disable those writes before revoking TaxiCRM's booking privileges. The existing `AUTOCAB_WEBHOOK_PROCESSING_PAUSED` flag covers immediate and scheduled webhook processing only.
- Need A Cab Plus currently keeps its accepted customer booking attempt in `web_booking_attempts` and, when its no-copy flag is off, writes a separate lowercase `bookings` row. That local model cannot replace canonical `Booking`. After the shared database cutover, preserve the attempt record for safe retries, resolve the accepted external booking ID to the canonical record, and keep all search and customer-history reads on the canonical table.
- The prepared `needacabplus_shared_app` role currently has read access to TaxiCRM tables, while `taxicrm_shared_app` has write access. This is suitable only for a database-location transition with TaxiCRM still as the sole canonical booking writer. A subsequent writer handoff must grant the Need A Cab Plus role the necessary booking-table writes, revoke those writes from TaxiCRM, and test both applications before the change is considered complete.
- A future Autocab/Local operating switch must be recorded per booking. Changing the default mode must not move an active booking to another dispatch engine.
